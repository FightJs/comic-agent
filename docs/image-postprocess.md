# 批次自动实图检查与一轮剧情返修

2026-11-06增量。完整Pi集成仍实施中；本功能调用现有图像服务与Pi视觉入口，不是供应商质量验收。最新验证与限制见`docs/pi-progress.md`。

## 操作与授权

在生图包“批量图像预览”中选择“本批检查与返修”：

- **仅生成候选**：沿用原链，每格一次图像请求，无自动检查或返修。
- **生成后检查实际像素**：每格一次生成、一次视觉检查，问题交人工。
- **检查并允许一轮严重剧情返修**：每格最多两次图像请求、两次视觉请求（原生成/初检/必要的一次返修/复查）。只有结构化报告同时为`critical`和`story`才触发返修；普通瑕疵、身份/服饰问题等不自动修。复查仍有严重问题也不会再修第二轮。

可选原著片段；没有片段时只检查固定包、绑定脚本和批准图像，不声称核对全书。预览固定视觉供应商/型号、文本依据、所选原文解析范围及当前审核Skill规则闭包。固定依据首先显示可读文本、引文与规则，完整原始记录可另展开。生成引用与前图合计最多7张用于自动检查，不静默删图；超限先拒绝预览。每张视觉图片最多4MiB、合计6MiB，沿原视觉服务限制，超限不压缩或偷偷截断。

确认前分别查看全批图像/视觉调用上限，勾选明确授权才执行。每格首次生成最多一次；所选检查与有限返修另计上限。费用未知，上限不表示一定调用。更改策略须新建预览，恢复不能扩大策略或范围。

原图和返修图都保留为未采用候选，视觉报告不写人工审核状态。可查看各自精确任务与完整只读报告（实图、固定参考、原著、规则、问题证据和原始返回）。完成仅指授权流程结果保存，普通问题与一轮后余留明确交人工。前图依赖等待父格检查/返修流程完成，若发生返修则使用最终返修候选的原调用像素，仍须人工采用、审核后明确恢复；不会自动把旧原图或其他图片当作依赖。若人工决定保留原图作为另一个制作方案，需明确调整后继包的已有前图引用并重新预览，不能静默改绑。

## 故障、容量与恢复

图像容量1、视觉容量1，各有独立槽位；图像落盘后释放生成槽。等待视觉时其余就绪格仍可生成，不让视觉请求占图像槽。批次结束前等待已派发的检查/返修，任何未知或未完成流程使本批“需核对”；其他独立分支可完成。

未知无原返回、格式无效、内容拒绝均不自动重发/重试/返修。明确恢复沿原review id、repair job id和call id；成功候选/报告跳过，已保存原返回恢复登记，不另生图。应用重启不派发，视觉在途状态按原服务标未知，未提交检查可在原批次明确恢复。图像批次有效预算及暂停见`docs/image-batch-control.md`；完整全局token/金额预算尚未实现，也未实现“确认无图的网络失败最多四次技术重试”。

停止后不再派发视觉或返修，已发送请求的费用可能未知、返回仍保留；在途返修返回可以保存原文件但不登记新候选。输入/原图/参考版本及视觉配置在启动、容量等待结束及实际提交前复核；变更会阻止受影响新请求，不自动换模型。用户提前采用或改动候选也会暂停后续自动操作，以免在改变的基础上继续付费。

## 宿主实现

`backend/image_postprocess.py`使用固定流程，无自由agent循环；状态与冻结计划挂原image_jobs.payload.postprocess。`image_batches`派发后处理子任务并等待收口，异常与取消不得遗留后续派发。根图像job继续代表原图；repair_job_id和initial/final_review_id关联原账本，调用不复制。视觉记录带image_batch_id，独立视觉start/recover不能绕过批次付费授权；批次内的单图与返修job亦由原批次管理。

返修operation key为`repair:{root_job_id}`，视觉为`post:{root_job_id}:initial/final`，同一次操作不可换输入。底图是原生成的实际文件，参考、参数和图像型号保持原固定输入；问题以结构化证据附加到原完整prompt，明确区域只是估计，不作为硬蒙版。超出提示词上限交人工，不截断问题以伪造完成。返修仅产生独立候选，保留原图与原调用；来源包含模拟时继续继承。
